# T3 Code

How the lead and tasks of *Lead and tasks* in [SKILL.md](../SKILL.md) run in
[T3 Code](https://t3.codes), the slot `plugins/haywire-dev/orchestrators/t3/` and the
repository's `t3.json` (ADR 0090). A T3 session carries `CLAUDE_CODE_ENTRYPOINT=t3-code`
and `T3CODE_THREAD_ID`; the session-start hook then names this file. T3's tools
(`t3_thread_*`, `link_pull_request`, …) load late: find them with the tool search.

## The places

- **The lead** is a T3 thread on the project root (the main folder).
- **A task** is a T3 thread in a worktree of its own, started by the lead with
  `t3_thread_launch`. T3 puts core worktrees under `~/.t3/worktrees/<repo>/`. The thread's
  title is the task's name, its branch.

## Created

The lead calls `t3_thread_launch` with a new worktree from `origin/master`, the branch
`<kind>/<name>` and the brief as the first message. The setup script from `t3.json`, once
imported into the T3 project (*The user's T3 settings*), runs
`python3 scripts/worktree_setup.py` when T3 creates the worktree (`runOnWorktreeCreate`).
`t3.json` sets `async: false` on it so that T3 holds the agent until it exits, but the
import drops that field (pingdotgg/t3code#40325), so T3 starts the agent alongside it until
`async: false` is set again (*The user's T3 settings*). Either way the session-start
hook waits until the worktree has its `.venv` and studio port (up to 5 minutes). Do not run
the script again while T3's run is still going.

**A library task.** T3 cannot place a worktree beside the repositories, which a library
worktree needs. The lead creates it from the library's main folder with
`git worktree add ../<repo>-<name> -b <kind>/<name> origin/<default branch>`, runs
`uv sync` there and gives its studio a port, then starts the thread with
`t3_thread_launch` and `workspaceStrategy: existing_worktree` on that folder. T3 runs no
create script for a worktree it did not create. Not yet confirmed on a real library task:
check that the thread binds to the folder and report it.

## Messages

A task reports with `t3_thread_send` to the lead's thread id, which its brief carries; the
message arrives as the lead's next input, no polling. The lead links each task's PR to the
task's thread with `link_pull_request`, so the thread shows it.

## The view

`tasks.py` shows no session column for T3: T3 has no slot `agents.py`. The lead reads its
task threads with `t3_thread_list`, `t3_worktree_list` and the PRs linked to them.

## Merged

The task runs `finish` after "merged", as everywhere. The settle script from `t3.json`,
once imported into the T3 project, runs each time a worktree thread settles: from the main
folder it runs `finish <branch>`, which removes the worktree and both branches, or removes a
worktree left detached. `finish` refuses before the merge, so an early settle removes
nothing.

**Re-settle after a merge.** A task thread can settle by itself before its PR merges (when
its last turn ends); the settle script then finds the PR unmerged and leaves everything.
So after each merge the lead unsettles the task's thread and settles it again, which runs
the settle script once more, now with the PR merged.

## The user's T3 settings

The session-start hook (`plugins/haywire-dev/orchestrators/t3/session.sh`) checks them in
every T3 session, the lead's included, with the slot's `doctor.py`, and says what is
missing; pass that list to the user in your first reply, before other work. Your reply is
what reaches the developer: T3 does not display the hook's `systemMessage` (observed
2026-11-20); the hook keeps it for hosts that do, such as the Claude Code CLI.

- **Items marked `[fix]`**: a `t3.json` script missing from the ones T3 runs, or one that
  differs from `t3.json` (`async: false` on *Worktree setup*, which T3's import drops,
  pingdotgg/t3code#40325). Offer the fix the hook names
  (`python3 <slot>/doctor.py --fix`) and run it only on the user's yes; a lead or task asks
  through the user, never on its own. It backs up `~/.t3/userdata/settings.json` beside it,
  changes only those scripts in `projectSettingsOverrides.<projectId>.defaultProjectScripts`
  (the list T3 runs while `projectSettingsFolded` is `true`), and prints what it changed.
  T3 keeps a hand edit made while it runs. Pass its output to the user.
- **The other items** the user does in T3; give each with the link the hook gives
  (`docs/collaboration/orchestrators/t3.md#setup`):
  - *Project settings → Actions → Import scripts → Import from t3.json*, once, when no
    script is imported yet or the folder is not a T3 project. The *Import scripts* button
    shows only while some `t3.json` script is not imported. Never import them with
    `t3_project_update`: it writes elsewhere, though `t3_project_read` echoes its write back
    (pingdotgg/t3code#14991).
  - *Settings → Worktrees → Cleanup*: *Delete merged worktrees* on; *Keep worktrees with
    local changes* on, set to *Uncommitted changes*. When T3 removes a merged worktree
    before the task ran `finish`, `finish <branch>` from the main folder (or
    `finish --sweep`) still deletes the branches.
  - Branch naming: the model's semantic prefix (`feat/`, `fix/`, `docs/`, …), the
    repository's `<kind>/<name>`.
  - Whether T3 honours these two when set in the file is not known, so `doctor.py` leaves
    them to the user.
- *Storage cleanup* (off by default) has no hook: it removes only worktrees T3 created and
  keeps their branches, so `finish` (or `finish --sweep`) still deletes the branches.

`doctor.py --check` prints the list again without changing anything. It reads T3's
internal, undocumented settings file, and T3's state database to find the project; a T3
update can break it. A file it does not recognise it leaves untouched and says so.

## A second machine

A linked environment: `t3_thread_launch` with its `environmentId` starts a thread, worktree
included, on that machine. The second machine's lead is a peer, as in
[second-machine.md](../second-machine.md).
