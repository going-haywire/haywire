# The stage view

**Context.**

- Slice 4 made a node's position a props field and introduced the layout channel ([ADR 0053](0053-position-lives-in-props.md)), so a second set of layout fields could sit on the same node. Slice 5a uses it: a node can be put on a graph's **stage**, a second arrangement for looking at and operating a graph.
- The spec left open where the stage's extent lives, how stage coordinates are measured, how a level shows two views, and what an unlocked stage view may do.

**Decision.**

- **The stage is a second layout channel.** `STAGE` (`haywire.core.node.layout`) names the `stage_x`/`stage_y`/`stage_width`/`stage_height`/`stage_size_adapt` props fields and adds three facts to the channel: which nodes it includes (`member="on_stage"`), where its origin sits on the canvas (`origin=200.0`), and that it draws its nodes with only on-stage pins and only on-stage edges (`stage=True`). `PATCH` has `member=None`, `origin=0.0`, `stage=False`. `CHANNELS = (PATCH, STAGE)`. The stage fields sit in a `"stage"` category of `NodeProperties` and are not in `REDRAW_FIELDS`. A file without them loads with every node off stage; there is no `format_version` bump.
- **Membership and origin.** A node is on stage when `props.on_stage` is true; it then has one stage rect. A stage canvas draws it with its normal patch card (same skin and title), at the stage rect, with the stage row rule: a row only for a port that shows a widget. See the skin contract below.
- **Stage coordinates are relative to a fixed origin.** `stage_x`/`stage_y` are measured from the stage origin, which is stage `(0, 0)` and cannot be edited. `STAGE.origin` is only the canvas margin it is drawn at. Positions are translated at two places only: the visual layer (outbound, `LayoutChannel.to_canvas`) and the interaction handler (inbound, `from_canvas`). A corner bracket marks the origin, and drags stop at it, so nothing sits above or left of it. The canvas takes two props, `originX`/`originY` (default 0: no marker, clamp at 0); no JS event changes. **Add to Stage** places a node at `x = STAGE_MARGIN`, below the lowest stage node (`next_stage_spot`, `haywire.core.graph.stage`); **Remove from Stage** clears `on_stage` and keeps the rect.
- **Extents per channel.** `BaseGraph.canvas_extent(channel)` holds one extent per channel: the patch's stays `canvas_width`/`canvas_height`, others live in a per-channel map. The canvas-size check measures only the nodes a channel includes and adds its origin. `ValidationResult.canvas_sizes` maps a channel name to its extent, and a canvas applies only its own. This resolves the earlier trap that `canvas_width`/`canvas_height` are the patch's.
- **Two keep-alive views per level.** Each open level holds a canvas per view in an inner `ui.tab_panels(...).props("keep-alive")`. The stage canvas mounts on the first switch to it; after that both stay mounted. Reason: switching must not re-render either view (the same `UINode` objects survive Patch, Stage, Patch), and a deactivated panel's DOM is detached, so the page-global pin uuids of a node shown in both views never collide. The selection is shared between the views (see below). The lock, the session claim and a gesture's claim act on the visible canvas; re-keying, pruning and teardown act on both. The first canvas a level mounts reports compatibility; the later one does not.
- **The switch.** A Patch | Stage switch sits in the editor header next to the lock button; `ToggleStageView` (`Mod+Shift+E`, `AccessTier.VIEW`) toggles it; `Mod+Alt+E` is Firefox's developer tools. The switch is a segmented control that marks the view now shown (the `hw-shell-toolbar-btn` tokens, `aria-pressed`, a tooltip on each segment); clicking the active segment does nothing. `GraphProperties.open_view` (`patch` | `stage`) is the open-in default, next to `open_locked`. A stage canvas with no nodes centres on the origin corner.
- **The stage is a display, not a mode.** Editing in stage view is exactly editing in patch view: paste, duplicate, cut, node creation, edge creation and reconnection, every context menu, every toolbar panel and every editor command run at the same access tier. The lock and the tiers apply to both views alike; a locked stage view caps the session at `operate` like a locked patch view. Delete is not remapped: in stage view it deletes the node from the graph, as in patch view; Remove from Stage is its own verb. Only the display differs: the on-stage nodes, at their stage rects, with only on-stage pins and edges (see the skin contract). Edges on stage are editable like any edge, and the edge context menu works there; since stage view draws only on-stage edges, those are the only ones it reaches.
- **Skin contract: `on_stage`.** `BaseSkin.render(self, main_card, wrapper, *, on_stage: bool)` takes a required keyword, so a skin outside the repo breaks loudly instead of silently. `render_pin(..., on_stage: bool)` also takes a required keyword; with `on_stage=True` it returns `None` for a port whose `port.on_stage` is false, otherwise it behaves as before. `render_ghost_pin` is unchanged, so an orphaned edge keeps its home. A skin's collapse check is `self.is_collapsed(wrapper) and not on_stage`: a node collapsed in the patch is drawn expanded on stage. Folds work on stage: the fold header draws under the same widget rule as any port (`port.should_show_widget()`, since a `FOLD` port has no `widget_key`; hidden when its widget is hidden), the open or closed state is honoured so a closed fold hides its children, and the state is the node's one fold state, shared with the patch. The split skin's config band honours fold state too and draws no band when none of its configs shows a widget; the split skin draws no fold header in either view. `SkinFactory.render(key, wrapper, *, on_stage=False, ...)` forwards the flag to `render` (the error-skin fallback too); `UINode._render` passes `channel.stage`. `render_stage`, `_render_stage` and the frameless default face are deleted.
- **A stage row is a widget row (amends 05a-2, "same rows" superseded).** On stage, a default-skin card draws a port's row only if the port renders a widget there: label plus widget, as in the patch (`NodeSkin._shows_widget`). A port without a shown widget draws no label and no row. An on-stage pin without a widget (an annotation swinglet on a default-skin node) draws its pin only, seated in a bare pin row so it keeps an anchor. The Annotation skin keeps its card, text, annotation pins and ADD slots. The title bar is unchanged; ghost pins stay; collapse stays forced off.
- **The selection is shared between the views.** Switching views no longer clears the selection (this replaces 05a). The shown canvas carries it over pruned to the nodes it draws (`GraphCanvasManager.show_session_selection`); the active node and component carry over when still shown, so no invisible node stays selected. `canvas.vue` resolves node, pin and edge elements inside its own `$el`, because ids repeat across the two canvases of one level.
- **Nodes made in stage view land on stage (Q7a).** A node created, pasted or duplicated while a stage canvas is active is put on stage at the gesture position in stage coordinates (the click, the paste point, or an offset from the original for a duplicate). Its patch position follows its siblings instead of copying those numbers (`patch_position_for_stage`, `haywire.core.graph.stage`): the patch centroid of the on-stage nodes plus the node's stage offset from their stage centroid. With nothing on stage yet, it is the centre of the level's patch canvas viewport (`ZoomPanContainer.get_viewport_centre`) when mounted, else the centroid of all patch nodes, else the stage numbers. Paste keeps the pasted nodes' relative layout in both views; a duplicate is the original's patch position plus `DUPLICATE_OFFSET`. Mirrored in a patch canvas (`stage_position_for_patch`, `haywire.core.graph.stage`): pasted nodes with `on_stage` keep their relative stage layout, anchored at the stage centroid of the on-stage nodes plus the anchor's patch offset from their patch centroid (the next free stage spot when the stage is empty, `next_stage_spot`); nodes without `on_stage` stay off stage. A duplicate of an on-stage node gets the original's stage position plus `DUPLICATE_OFFSET`. Every computed placement clamps its group's min-corner to at least `(0, 0)` in the channel it targets, keeping the relative layout, so nothing lands above or left of the stage origin (patch drags clamp at 0 too); this covers both mirrors and stage-canvas creation left of or above the origin. Creating a node in the patch still leaves it off stage. This is one undo step with the creation (`with_stage_placement`, `haywire.core.node.layout`). It covers the background menu and add-node search, drop-to-create from an edge drag, the New Node wizard, paste, duplicate and splitting an edge with a reroute. Collapse to Group, macro placement and detach are selection-driven, carry no click position, and do not land on stage.
- **`on_stage` and `NODE_STAGE_CHANGED`.** `on_stage` is a bool props field. A write to it raises `ChangeReason.NODE_STAGE_CHANGED`, which is save-relevant, not visual-only, and does not reassemble. The stage canvas mounts or unmounts the node (and its eligible edges) on that reason; the patch canvas ignores it. The node also re-measures the stage extent. `SetStageMembershipAction` writes the position, the size mode and `on_stage` last, so a canvas mounts at the final place, and undoes as one step.
- **On-stage wires are a `WireType` class attribute.** `WireType.on_stage: ClassVar[bool] = False`, `True` on `AnnotationWire`. `DataPort.on_stage` and `EdgeWrapper.on_stage` derive it the way `wire_key` and `carries_values` do. A stage canvas registers an edge only when `edge.on_stage` is true and both end nodes are on stage, and applies that filter at every place it counts or iterates edges. There is no decorator.

**Considered options.**

- *One keep-alive panel per level that re-mounts the canvas on every switch.* Rejected: every switch re-renders the whole view.
- *One canvas that swaps its channel.* Rejected: it would rebuild every node card on each switch and cannot keep both views' edges drawn at their own pins.
- *Stage coordinates in canvas space.* Rejected: a node at `(0, 0)` would not sit at the origin, and a moved origin would shift every saved position.
- *A grey band left of and above the origin* (the spec). Replaced by the corner bracket plus a drag clamp.
- *Delete in stage view means Remove from Stage* (the spec). Rejected by the user: it hides a destructive verb behind a familiar key. Remove from Stage is a separate row.
- *`@wire(on_stage=True)`.* Rejected: wire types are plain classes with class attributes; no decorator exists.
- *Arrange-only stage view, gated by an allow-list* (slice 5a as first built). Rejected by the user on 2026-10-15 after the live check: it refused edits the user wants (paste, creation, connectors), and a second set of rules for one canvas is a mode the user never asked for. The stage is a display.
- *The patch position copies the stage numbers* (05a-2). Replaced on 2026-10-15: stage coordinates are small and origin-relative, so the node landed far from its siblings in the patch.
- *Same rows on stage as in the patch* (05a-2). Superseded by the widget-row rule: labels and rows without a widget are clutter on a display.
- *On stage a fold's state is ignored: no header, every child drawn as if open* (5a-3). Rejected by the user on 2026-10-15: a fold and its hiding and showing of widgets make sense without pins. Replaced by the widget rule above.
- *A frameless `render_stage()` face* (slice 5a as first built). Rejected by the user on 2026-10-15: it drew a node without ports as nothing and an annotation as a column of pins. The patch card, with only the on-stage pins drawn, keeps every row and label.

**Consequences.**

- A graph's stage extent no longer touches `canvas_width`/`canvas_height`; code reading `ValidationResult.canvas_size` reads `canvas_sizes` by channel name.
- Renaming a keep-alive panel remounts it, so `Slot` names each document panel by a stable uuid (`Slot._panel_names`), not by binding id; Save-As changes only `data-hw-binding`, and the canvas keeps its edges and viewport.
- Two canvases per level means every call site of a level's canvas must name which one it means.
- Slices 5b (on-stage connector editing, annotation text editing, Add Annotation), 5c (stacking order) and 5d (control nodes) build on this channel.
