# Graphs own a settings tier: GraphSettings, chained mirrors, framework < graph < node

**Status:** Accepted.

Settings came in three flavours — `FrameworkSettings`/`LibrarySettings` (persistent, resolved through the registry's workspace/global tiers) and `NodeSettings` (per-node-instance, serialized with the graph). A graph author who wanted every node in one graph to default to a particular skin had no graph-scoped place to say so: either change the framework default (affects every graph) or override the skin on each node individually. `settings-arch.md` §10 listed a "per-graph settings tier" as an open question. This ADR records the fourth flavour that answers it, plus the mirror mechanism the interposed field needed.

## Decision

**`GraphSettings`** is a fourth `Settings` subclass, parallel to `NodeSettings`: per-instance `DataField` cells, never registered with `SettingsRegistry`, a `_graph` backref instead of `_node`. `_node` stays `None` unconditionally, which structurally disables every node-only surface (promotion, the setting-row menu's promote entries) without a special case in those surfaces — they already gate on `obj._node is not None`.

**`GraphProperties`** is the one framework-provided bag, instantiated by `BaseGraph.__init__` as `graph.props`, wired to the registry from `get_settings_registry()` — called unconditionally, the same precondition `NodeData.__init__` already has. There is deliberately no constructor-level override (an earlier draft added a `settings_registry=` parameter for test convenience and a try/except tolerating no-DI construction; both were removed — see "Rejected alternatives" below). Tests that need an isolated registry call `set_settings_registry(...)` on the ambient DI context before constructing a graph, exactly as existing node-focused tests already do. Its `default_skin` field shadows the framework studio-skin setting via the **existing** registry-key mirror (`shadow()`) — the graph→framework hop needed no new machinery.

**Chained mirrors realize the tier.** A node field mirrors a `GraphSettings` field via a new factory, **`graph(src=...)`**, parallel to `shadow()`/`watch()`. `graph()` validates eagerly — `TypeError` unless `src._owner_cls` is a `GraphSettings` subclass — and marks the descriptor via an explicit `is_graph_mirror` flag, rather than inferring "which mirror mechanism applies" from the shape of `src`. This was a deliberate correction mid-design: the first draft inferred graph-mirror-ness from "`src` has no registry key," which is correct but non-local (a reader must know `GraphProperties` happens to be a per-instance flavour to predict the field's behavior) and un-typo-safe (a plain `shadow()` pointed at the same field would silently do the wrong thing). The explicit factory fails at class-definition time instead of at some later, harder-to-attribute moment.

**The graph mirror's runtime mechanism** (`Settings._graph_src_cell`, `_owning_graph`, `_subscribe_graph_mirror` in `settings.py`) keeps the node field's **own** cell and *listens* to the src field's cell on the owning graph's bag — it never borrows the graph's cell. "Unset tracks, set ignores" applies at seed (`_cell_for`), subscribe, reset, and cleanup, composing transitively with the registry-key hop below it: a framework change reaches an unset node only by passing through an unset graph bag first.

**The lookup seam** is `BaseGraph.settings_bag_for(owner_cls)` — "which of my bags is an instance of this class." A node field's mirror walks `node → wrapper → graph → settings_bag_for(src's owner class)`. Plain class matching is safe here because `GraphProperties` lives in haywire-core, which never hot-reloads (unlike `LibrarySettings` schemas, where class objects are replaced on reload and object-identity matching would silently break).

**Detachment contract.** A `graph()` field on a bag with no reachable graph — no node, node not in a graph, graph lacking the src bag — holds its descriptor default and is **not live**. There is no registry fallback. This was also a mid-design correction: the original design (and the shipped spec/tickets) called for a headless bag to fall back to live-tracking the *terminal* registry key, "byte-for-byte" matching a direct framework shadow. That fallback was cut once grep confirmed it defended a scenario with zero consumers — no test, no UI harness route, and no production code path constructs a detached `NodeProperties` (a `NodeWrapper`'s graph is a non-optional constructor argument). The fallback would have added a second subscription channel into `_on_field_change`, doubling that method's branching and creating exactly the kind of two-channel-driving-one-field bug surface a reviewer would need to reason about for a case that cannot occur. An honest descriptor default on a detached bag is also easier to debug than a plausible-looking value that happens to be stale — it surfaces the detachment instead of masking it.

**`_on_field_change` is untouched.** Graph mirrors never ride the registry notification channel; only the pre-existing registry-key mirror path uses it. This is a direct consequence of dropping the terminal-key fallback above, and it is the reason the feature could land without touching the highest-risk existing method in the file.

**A plain `shadow()` pointed at a `GraphSettings` field fails loudly.** If a `_mirror_descriptor` exists but carries no registry key and the descriptor was not built via `graph()` (so `is_graph_mirror` is `False`), `_subscribe_setting` raises `TypeError` naming the fix. Without this guard, the mistake would silently produce a field that never tracks anything — never fires, never resolves, sits at whatever its cell happened to seed with.

**Serialization.** `BaseGraph.to_dict()` gains a `"props"` key (the bag's existing `to_dict()` — locally-set values only). `load_from_dict` restores it immediately after `clear()` and *before* the nodes loop, so node-bag graph mirrors seed correctly at node-construction time. Absence of the key (pre-feature graphs) is valid and restores nothing (`reset_all()` runs first for the reused-live-graph case).

## Rejected alternatives

- **Library-registered graph bags.** Considered and deferred: letting libraries declare their own graph-scoped bags (parallel to how they declare `LibrarySettings`) would need a registration path plus a hot-reload story for rebinding every open graph's live bag instances and every node's cell subscriptions into them on library reload. `GraphProperties` living in haywire-core sidesteps this entirely (never hot-reloads). The risk was judged not worth taking for a first bag with a single field. `settings_bag_for()` is the seam that keeps this addable later without reworking the mirror mechanism — it changes to a lookup-by-identity, everything else is unaffected.
- **Registering graph bags in the SettingsRegistry with per-graph keys.** Would let the graph→node hop reuse the registry-key mirror channel uniformly, but pollutes the app-wide registry with one key set per *open graph instance* (not per class), requires register/unregister on graph open/close, and a class-level `shadow(src=...)` declaration cannot name a per-instance key at class-definition time anyway.
- **The node field borrowing the graph's cell instead of listening to it.** Rejected because "unset tracks, set ignores" requires the node's cell to be able to hold either the tracked graph value or a diverged local override — a borrowed shared cell cannot represent both states for two different bags simultaneously.
- **Lazy resolve-on-read mirrors** (skip the cell machinery; compute the answer at `__get__` time since skin is read comparatively rarely). Rejected because it reintroduces exactly what ADR 0013 removed: a promoted port shares the field's cell by reference (`bind_field`), so the cell must hold the live answer or a promoted skin port propagates a stale value; and widgets bind the cell directly (`SettingWidgetModel`), so a lazy field would need a second binding mode. Notification is also unaffected by laziness — the subscription chain that makes the canvas restyle live is required either way, so laziness would only remove the cheap final write, not the machinery around it.
- **A `settings_registry=` constructor parameter on `BaseGraph`, tolerant of no DI configured (try/except around `get_settings_registry()`).** This was the first cut and was rejected on review: it added a second, `BaseGraph`-only injection mechanism for a concern (get the ambient settings registry) that `NodeData.__init__` already solves the same way every other node-focused test does — by configuring the DI context (`set_settings_registry(...)`) before construction, not by threading a registry through the constructor. Adding a parameter purely to make tests convenient, when the sibling class (`NodeData`) has no such parameter and no such tolerance, is exactly the kind of test-driven constructor growth this project avoids. `BaseGraph.__init__` now matches `NodeData.__init__` exactly: `get_settings_registry()` is called unconditionally and raises `RuntimeError` if DI isn't configured — there is no bare, no-DI construction path for a graph.

## Consequences

- Resolution for the node skin field (and any future interposed field) is `framework < graph < node`, live at every hop, with `reset()` returning to the tier immediately below.
- `docs/architecture/settings/settings-arch.md` §10's open question is resolved; §6.1's schema-class table gains `GraphSettings`; §7.3's notification flow gains the graph-mirror hop.
- `docs/components/settings/setting-canon.md` documents `graph()` as the third mirror factory alongside `shadow()`/`watch()`.
- No change to `SettingsRegistry.resolve()`, the workspace/global tier dicts, or JSON persistence at the registry level — this is purely a new *instance-side* mirror kind plus one new graph-owned bag.
- The one real graph-discard site found (`HaystackState.remove_entry`, which closes a single graph tab for good) now calls `graph.cleanup()`; `GraphAppState.unregister` deliberately was NOT used for this — its own docstring states it holds references only and owning libraries are responsible for lifecycle.
- **`NodeDefaultSkinSettings` moved from `haywire.ui.skin.settings` to `haywire.core.skin.settings`.** Adding `graph/properties.py`'s import surfaced a pre-existing core→ui layering violation: `node/properties.py` already imported `NodeDefaultSkinSettings` from `haywire.ui.skin.settings` at runtime (not `TYPE_CHECKING`-guarded), and this feature was about to add a second such import rather than fix the first. Inspection showed `ui/skin/settings.py` had no actual dependency on `ui` — it is a plain `FrameworkSettings` schema (imports only `haywire.barn`, `haywire.core.namespaces`, `haywire.core.settings`), unlike its sibling `ui/skin/base.py`, which genuinely imports `nicegui.ui` for rendering. The file's location under `ui/` was the actual bug, not a necessary coupling: skins split cleanly into a *schema* half (which skin is selected — core-shaped) and a *rendering* half (how a skin draws a node — ui-shaped, stays in `haywire.ui.skin`). Moving the schema half to a new `haywire.core.skin` package (parallel to `haywire.ui.skin`) fixed the violation at its root for both consumers instead of tolerating it in a second file.
