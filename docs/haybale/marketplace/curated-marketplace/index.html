    The curated marketplace¶

    Settled by inquisition on 2026-08-27. Unbuilt.

    going-haywire/marketplace is a second, separate feed publisher. It carries first-party standalone libraries (going-haywire/haybale-visiongraph and its siblings) and a selected few third-party libraries, in three channels that differ only in what they assert about which version.

    It is not the Official feed. It never carries the lockstep monorepo libraries, and it hosts no packages — PyPI serves every artifact.

    1. Two feeds, two jobs¶

    Official feed Curated marketplace
    Repo going-haywire/haywire going-haywire/marketplace
    URL going-haywire.github.io/haywire/marketplace.toml going-haywire.github.io/marketplace/<channel>/marketplace.toml
    Carries the lockstep barn/* libraries first-party standalone + selected third-party
    Shape two-tier ([[stalls]] + stalls/*.toml) inline [[haybales]], one file per channel
    Generated by scripts/generate_marketstall.py on each release tag the marketplace repo's own generator

    They stay different shapes. The monorepo's feed is regenerated on its own release cadence and unifying the two would mean rewriting it for no subscriber benefit. A fresh install subscribes to both: the Official feed for the framework's own libraries, the curated stable channel for everything else.

    2. Rows are carried by value¶

    A curated row is generated in CI by reading haybale.toml out of the artifact being pinned — the wheel, unzipped. It is never a link to the author's own marketstall.toml.

    The reason is identity. A [[stalls]] URL delegates the row's contents to the author, including install_spec. An author (or anyone who takes their repo) can keep name = "haybale-foo" and repoint install_spec at a different distribution, and every subscriber follows on the next refresh. Reading the metadata out of the wheel makes the row and the payload the same object: a row cannot disagree with what it installs, because it is what it installs.

    That yields one hard invariant:

    Every field in a curated row comes from the artifact. The curator authors none of them.

    No exceptions — not even an advisory [deprecated] note. A library the curator wants gone is removed from the registry, not annotated.

    3. Pip only, both parties¶

    Curated entries must be pip-installable. Not because third-party authors are less trusted than first-party ones, but because only one of the two coordinate kinds is immutable:

    what is immutable is pinning by tag enough?
    pip the artifact — PyPI forbids replacing a published version. It can be deleted or yanked, but never become something else yes, once name==version is asserted by someone other than the author
    git only the commit SHA — git tag -f && git push --force repoints a tag, and the payload moves with it no, whether pinned by reference or by value

    A compromised going-haywire account moves a tag exactly as easily as a stranger's. So the rule follows the coordinate, not the author, and applies to first-party libraries too.

    The monorepo already proves the position is livable: git_publish_order = [] in pyproject.toml — everything it releases goes to PyPI.

    distribute¶

    haywire share gains a project-scoped declaration in the repo pyproject:

    [tool.haywire.marketstall]
distribute = "pypi"   # or "git" (default)

    It decides what every row of that repo's marketstall.toml carries:

    distribute source install_spec
    "git" (default) "git" haybale-foo @ git+https://…@v1.2.3#subdirectory=barn/haybale-foo
    "pypi" "pypi" haybale-foo==1.2.3

    Project-scoped rather than per-library, because the unit of publishing is the project: one tag, one marketstall, one distribution mode. Declared rather than probed — a probe of PyPI is wrong for exactly the first release, where the name is not registered yet. Preconditions verify it, so "pypi" against an unregistered name is caught before a tag is pushed.

    One coordinate per version¶

    identity_matches treats PyPI-vs-git as a name conflict, never the same library. Without distribute, an author's own stall would advertise a git coordinate while the curated feed advertises a pip one, and a user subscribed to both would be asked to block one of two rows describing the same release. One declaration, one coordinate, no conflict.

    4. The three channels¶

    Same membership, three assertions.

    channel version asserts cadence
    edge unpinned — resolves at install time membership + identity nightly regeneration
    latest == newest at curation-tag time + installs and loads on its own curation tag
    stable ==, resolver-solved + the whole set resolves and loads together framework releases

    edge is regenerated nightly even though its install_spec floats, because updates_available compares installed < version — a frozen version field would mean edge subscribers never see an update offered.

    Why stable is the only one that can promise co-installation¶

    Libraries install into the project's single venv, one at a time: uv pip install <install_spec> -c <framework-constraints> (barn/haybale-marketplace/haybale_marketplace/library_manager.py:510). The constraints file pins only the framework packages (haywire-core, haywire-studio, nicegui — barn/haybale-marketplace/haybale_marketplace/library_manager.py:47).

    Because each install is a separate resolve, installing library B can quietly upgrade a transitive dependency library A needed at an older pin. Nothing detects it; A breaks at import time later. A set proven to resolve together is the only thing that closes this, and no runtime check can substitute for it.

    Placement is derived, never granted¶

    Nobody promotes anything. Once a library has membership it appears in edge on the next nightly; it reaches latest only if it installs and loads; it reaches stable only if the resolver can fit it alongside the rest. Membership is the only human decision in the system, which is what makes "why am I not in stable" answerable from a machine-produced record instead of a judgement call.

    5. What is deployed¶

    GitHub Pages at the repo root, mirroring how going-haywire/haywire serves its feed:

    https://going-haywire.github.io/marketplace/
├── index.html                          # landing page: the channels, what each asserts
├── edge/marketplace.toml               # [[haybales]] inline, unpinned specs
├── latest/marketplace.toml             # [[haybales]] inline, ==pinned at tag time
├── stable/marketplace.toml             # [[haybales]] inline, ==pinned, solved set
├── stable/<curation-tag>/marketplace.toml    # immutable archive
├── latest/<curation-tag>/marketplace.toml    # immutable archive
├── archives.html                       # the archive index — see below
└── stable-report.md                    # why each library sits at the version it does

    Inline [[haybales]], not two-tier. Refresh fetches a market body and then every [[stalls]] URL it lists, so a two-tier layout costs 1 + N HTTP requests per refresh. Inline costs one. The single-library subscription case that two-tier buys is already served by the author's own stall.

    The archive index is required, not polish. GitHub Pages serves no directory listings — /stable/ 404s unless an index.html exists there. Without archives.html a user would have to guess curation-tag names. It lists each archive with its tag, date, the haywire-core version it was solved against, and how many libraries it holds, which is what makes one choosable over another.

    6. What is in the repo¶

    registry/<dist-name>.toml     # membership — name, source, distribution. Human-edited.
stable.constraints.txt        # the curator's only knob on the solve
locks/latest.toml             # resolved set, written at curation tag
locks/stable.toml             # solved set + the framework versions it was solved against
scripts/                      # generator, solver, verifier
.github/
  ISSUE_TEMPLATE/add-library.yml
  workflows/                  # see §8 for the permission split

    One file per library rather than one registry file: submission PRs never conflict, removal is git rm, and per-library history is clean.

    Membership and pins have different owners, and the layout keeps them apart — humans edit registry/ and stable.constraints.txt, the toolchain writes locks/. The co-install proof is a property of the set, so it lives in a set-level lock rather than scattered across per-library fields where nothing would record which combination was proven, or against which framework.

    7. The stable solve¶

    solve_stable.py runs to completion without asking anything. A curator reads its output and either accepts it or writes a constraint; there is no intermediate state where a human has to choose a version.

    Inputs¶

    the membership names from registry/*.toml
+ haywire-core==X, haywire-studio==X, nicegui==Y
+ stable.constraints.txt
+ --universal            # libraries declare `os`; a set that resolves on Linux may not on Windows
+ --exclude-newer <ts>   # see below

    stable.constraints.txt is the curator's override, not the mechanism: pip-tools-style ceilings (haybale-x<2.0, a deliberate hold) and exclusions (haybale-x != 1.4.0, a version that failed the load gate). Every line carries a # reason. In a normal cycle it is not touched.

    The algorithm¶

    The resolver optimises nothing on its own. It returns a solution, preferring high versions in its own traversal order, so left alone it will silently hold one library three releases back to let an obscure one be current. The solve supplies the objective the resolver lacks, by expressing aspiration as floors:

    hard floor,  every library:  >= its current stable pin      # stable never regresses
aspiration,  every library:  >= its newest release

loop:
    resolve(hard floors + aspirations)
    success → done
    failure → the resolver's derivation names the conflicting libraries.
              relax ONE named aspiration to its hard floor, record why, loop.

    One resolver call per iteration, bounded by the number of libraries, and only the libraries the resolver named are ever candidates — so it settles in two or three calls in practice. Brute force is never needed and never affordable (N libraries × M candidate versions is Mᴺ); the resolver already searches that space with conflict-driven learning, and all we choose is what it optimises for.

    Which named library gets relaxed, in order:

    1. Whichever relaxation leaves the most libraries at their newest. Try each candidate, keep the best. This is the objective stated directly rather than through a proxy.
    2. On a tie, the more recently released one loses. The rest of the set was working; one release broke the fit, and its author is best placed to widen a constraint. Self-correcting — next cycle it is no longer the newest. The bias to accept is that a frequently-releasing library is more often the newer party and so is held more often.
    3. A constraint in stable.constraints.txt overrides both, for when policy has to beat arithmetic.

    Why not bump each library in isolation¶

    Testing one library at a time against a frozen baseline under-reports. If haybale-a 2.0 and haybale-b 2.0 both need numpy>=2 while the current pins hold both at 1.x needing numpy<2, then A alone fails, B alone fails, and both would be reported conflicted — when moving both together resolves cleanly. Libraries that must advance together are invisible to a per-library sweep, and fall out of the floor-relaxation loop for free.

    Reproducibility¶

    CI recompiles from scratch and fails if the committed lock differs from what the inputs produce — the same contract scripts/check_release_versions.py --expect enforces for release versions.

    That check is only sound if the resolution is time-pinned. A release appearing between the curator's solve and CI's would otherwise make the two disagree legitimately. --exclude-newer <timestamp> fixes it: the timestamp is written into the lock header and reused verbatim by CI. Same inputs, same instant, same answer.

    stable-report.md¶

    Generated beside the lock, served on Pages, and the document an author is pointed at when their newest release did not land in stable. One row per curated library: newest available, the version in the lock, and which of four states explains the gap.

    state source of the explanation
    held the constraint line and its # comment
    conflict the aspiration the solve relaxed, with the resolver's own derivation and what taking it would have cost — "taking 1.4.0 would have forced haybale-y and haybale-z back; the clash is numpy (x wants >=2, y wants <2)". Produced by the relaxation loop, not a separate pass
    failed-load the import error from the load gate
    not-yet-considered released after the last curation tag

    Yanking does not protect a pin¶

    Under PEP 592 a yanked release is ignored by resolvers unless the requirement pins it exactly with == — which every stable and latest row does. An author's yank therefore cannot reach subscribers on its own. The verify job queries the PyPI JSON API for yanked on every pinned version and fails the lock when one is yanked.

    8. Gates, and the permission split¶

    Installing a wheel does not execute code. Importing it does. The workflows are split on that line, and the split is the security boundary:

    tier permissions does
    privileged contents: write, deploys Pages unzips wheels, reads haybale.toml, resolves, generates rows, deploys
    untrusted permissions: {}, no secrets, pull_request trigger installs and imports each library, asserts its components register

    Row generation never needs execution — reading haybale.toml out of a wheel is unzipping. So the tier that can write has nothing to gain from running submitted code, and the tier that runs submitted code has nothing to steal.

    Getting this boundary wrong turns a curated marketplace into a supply-chain vector aimed at its own subscribers. It is the one thing in this design that must be built deliberately rather than discovered.

    Gate contents:

    • Metadata (privileged) — the distribution resolves on PyPI; the wheel contains a haybale.toml that passes the strict reader; a haywire.libraries entry point is declared; the name is not already claimed by another registry entry or by the Official feed.
    • Co-install proof (privileged) — one uv pip install of every candidate install_spec at once, into a clean env with the framework pinned. Resolution only, no execution.
    • Load check (untrusted) — import each library, assert its components register.

    9. Submission, review, removal¶

    Request. A GitHub Issue Form (.github/ISSUE_TEMPLATE/add-library.yml) with structured fields: distribution name, source repo, contact. A workflow parses the issue, writes registry/<name>.toml, runs the gates, opens a PR that closes the issue, and comments the verdict back on the author's own issue. No fork, no git, no schema knowledge required.

    Accept. @going-haywire/curators owns registry/, stable.constraints.txt and locks/ via CODEOWNERS, and merges. The reviewable artifact is the PR — a diff plus a CI verdict — which is what makes branch protection do real work.

    What merging asserts, and this must be stated plainly in the repo's README:

    1. The distribution exists on PyPI and its wheel contains a valid haybale.
    2. This name maps to this distribution.
    3. For stable: this version resolves alongside the rest of the set and imports cleanly.

    It asserts nothing about whether the code is safe, reviewed, maintained, or correct. Nobody reads the source. Unsaid, "curated by going-haywire" implies a review this design cannot back.

    Update. No author action. edge picks up new releases nightly; latest/stable at the next curation tag. A scheduled job opens an issue listing curated libraries with releases newer than the stable lock — purely informational, making no decision, and the notification that starts a cycle.

    Removal. git rm registry/<name>.toml. The row vanishes from the next generation; subscribers' cached rows go stale=True on refresh; uninstalled ones become trash-icon removable; installed ones keep working. The reason lives in stable-report.md and git history — never in a curator-authored field.

    10. What changes in this repo¶

    change why
    distribute in [tool.haywire.marketstall], honoured by _build_entry_for_library §3
    Preconditions verify distribute = "pypi" against PyPI registration catch it before a tag is pushed
    Delete pypi_marketplace_url, its README marker line, and _update_repo_readmes' pypi_url parameter distribute = "pypi" makes the repo-root marketstall be the PyPI feed; the second surface and the Pages deploy it required are redundant. Deleted outright — it had no consumers
    generate_marketstall.py emits install_spec = "<name>==<version>" for pypi rows the bare name meant the row advertised one version and installed another, so updates_available showed a phantom update forever. check_require() already catches the old-framework case before the button does anything
    ensure_marketplace_config() writes a commented text template, not toml.dumps the default file is the one place a user is guaranteed to open, since hand-editing is the only way to change a subscription. It carries the other channel URLs commented out, the archive index URL, and one line on what each channel asserts
    Default subscriptions become Official feed + curated stable stable is the channel whose assertion matches what a default should promise

    Nothing else in the studio changes. There is no channel selector, no unsubscribe UI, and no auto-update.

    11. Non-goals¶

    • Never carries the first-party monorepo libraries. The Official feed keeps publishing those, and stays two-tier.
    • No git-sourced entries, ever.
    • No code review, security audit, or maintenance guarantee.
    • No wheel hosting or mirroring.
    • No studio UI beyond the default subscription.
    • No non-GitHub submission path.
    • No cadence promise beyond "stable advances at framework releases".
    • haywire share does not publish to PyPI. It cannot assume a GitHub remote, and PyPI registration needs human interaction regardless. Authors publish their own way; the docs explain how.
