# T3 Code

[T3 Code](https://t3.codes) runs Claude Code sessions as *threads*, each in the project
folder or in a worktree of its own. It is the maintainer's orchestrator. How the agents
use it is in [its agent page](t3-agent.md).

| Role | In T3 |
|---|---|
| The lead | A thread on the project root, the main folder |
| A task | A thread in a worktree, started by the lead with `t3_thread_launch`; its title is the branch |
| A report | `t3_thread_send` to the lead's thread |
| The task's PR | Linked to its thread by the lead (`link_pull_request`) |

## Setup

1. Add the repository's main folder as a T3 project. T3 reads
   [`t3.json`](https://github.com/going-haywire/haywire/blob/master/t3.json) at its root
   and applies its settings, but runs no script from it until it is imported. Import all
   three once, in *Project settings → Actions → Import scripts → Import from t3.json*; the
   *Import scripts* button shows only while some `t3.json` script is not imported yet. The
   scripts menu then lists them as *From t3.json*. Import them in the app, not with the
   agent's `t3_project_update`: on most installs T3 runs the scripts kept in its
   `settings.json`, and that tool writes elsewhere
   ([pingdotgg/t3code#14991](https://github.com/pingdotgg/t3code/issues/14991)).
   - **Worktree setup** runs `python3 scripts/worktree_setup.py` when T3 creates a
     worktree. `t3.json` sets `async: false` on it so that T3 holds the agent until it
     exits, but the import drops that field
     ([pingdotgg/t3code#40325](https://github.com/pingdotgg/t3code/issues/40325)); set it
     again after importing (below). Either way the session-start hook waits until the
     worktree has its environment and studio port, up to 5 minutes.
   - **Finish merged task** runs each time a worktree thread settles: from the main folder
     it runs `finish` on the thread's branch, which removes the worktree and both branches
     once the PR is merged, and refuses before.
   - **Haywire studio** you run from the scripts menu: it starts this worktree's studio on
     the port `worktree_setup.py` gave it (see *Starting the studio*).
2. Set `async: false` on *Worktree setup* again: the import drops it. The agent offers to
   do this for you (below). Without it the agent starts while the setup is still running,
   and the session-start hook's wait covers that.
3. *Settings → Worktrees → Cleanup*: turn on *Delete merged worktrees*, and *Keep worktrees
   with local changes* with *Uncommitted changes*.
4. Branch naming: the model's semantic prefix, so branches read `feat/…`, `fix/…`, `docs/…`.

### The agent checks the setup

Each T3 session, the lead's included, checks this setup at start and the agent lists what is
missing in its first reply (T3 does not show a hook's own message). It offers to add missing
`t3.json` scripts and `async: false`, and only on your yes runs
`python3 dev/orchestrators/t3/doctor.py --fix`, which backs up
`~/.t3/userdata/settings.json` first. The rest (the import, cleanup, branch naming) you do
in T3, steps 1, 3 and 4. `--check` lists the gaps without changing anything. The check reads
T3's internal settings file; one it does not recognise it leaves untouched.

## Starting the studio

The script *Haywire studio* runs in the thread's folder. It calls `haywire-studio` from the
[umbrella](https://github.com/going-haywire/umbrella#readme) (`bin/haywire-studio`, linked
onto your `PATH` once, as its README says), which starts the full studio with every library,
the worktree's own `packages/*` and `barn/*` included. Without it on the `PATH` the script
falls back to `uv run haywire`: the studio with this checkout's environment only. Either way
a worktree's studio uses the port `worktree_setup.py` wrote to its `.haywire/settings.json`,
so several run side by side; the main folder's is 8124.

## Things to know

- **After a merge the lead sends nothing to the task's thread.** This overrides the
  "merged" message of the neutral flow in [Lead and tasks](../lead-and-tasks.md): a message
  resumes the thread, and if its worktree is already gone T3 re-creates the worktree and the
  branch from local `master`
  ([#198](https://github.com/going-haywire/haywire/issues/198)). The lead checks `master`'s
  CI itself and re-settles the thread; the settle script runs `finish`. A task's brief
  promises no "merged" message.
- **A thread can settle before its PR merges**, when its last turn ends. Its settle script
  then finds the PR unmerged and leaves everything. After each merge the lead unsettles the
  task's thread and settles it again, so the cleanup runs. A thread that has not settled
  yet settles when its turn ends, and the script runs then.
- **Library tasks** need their worktree beside the repositories, which T3 cannot do. The
  lead creates it with `git worktree add ../<repo>-<name> …` and starts the thread on that
  folder (`existing_worktree`). Not yet confirmed on a real library task.
- **Storage cleanup** (off by default) has no hook: it removes only worktrees T3 created
  and keeps their branches; `finish --sweep` cleans those up.
- The task view (`tasks.py`) shows no session column for T3 tasks; the thread list does.
- A second machine joins as a *linked environment*; its lead is a peer.
- A worktree costs about 840 MB, most of it the `.venv`.
