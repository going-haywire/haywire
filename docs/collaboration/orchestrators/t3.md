# T3 Code

[T3 Code](https://t3.codes) runs Claude Code sessions as *threads*, each in the project
folder or in a worktree of its own. It is the maintainer's orchestrator. How the agents
use it is in [its agent page](t3-agent.md).

| Role | In T3 |
|---|---|
| The lead | A thread on the repository's main folder |
| A task | A thread in a worktree, started by the lead with `t3_thread_launch`; its title is the branch |
| A report | `t3_thread_send` to the lead's thread |
| The task's PR | Linked to its thread by the lead (`link_pull_request`) |

## Setup

Before you start with T3 you need: 

- T3 Code 0.1.11 or later (an older one drops a script's `async` on import, see *Things to
  know*);
- on the machine: `uv`, `git`, `python3`, `jq` (the hooks use it) and `gh`, logged in
  (`gh auth login`, then `gh auth setup-git`);
- the clones of the organisation's repositories (a contributor's forks), as in
  [A developer's workstation](../workstation.md),
    - with core as `haywire-repo` and
    - each library beside it, so that `../haywire-repo` reaches core from it. The parent
      folder's name does not matter.

Cloning is enough. Every repository already commits what a thread needs: its `t3.json` (the
scripts below), `.claude/settings.json` (the hooks) and `.mcp.json` (the Farmhand bridge).
Nothing is installed into T3 or Claude Code, and no `uv sync` is needed first: the bridge's
`uv run` builds a main folder's environment on its first start, *Worktree setup* a
worktree's. The [umbrella](https://github.com/going-haywire/umbrella#readme) is needed only
for the full studio (*Starting the studio*).

The setup has two parts: T3's own settings, once, and each repository as a T3 project.

### Once, in T3's settings

1. *Settings → Worktrees → Cleanup*: turn on *Delete merged worktrees*, and *Keep worktrees
   with local changes* with *Uncommitted changes*.
2. Branch naming: the model's semantic prefix, so branches read `feat/…`, `fix/…`, `docs/…`.

### Once per repository

Core and every library you work on is a T3 project of its own. For each, in this order:

1. **Add the project**: the repository's main folder (`haywire-repo`, `haybale-<name>`).
2. **Import the scripts**, in the app, not with the agent's `t3_project_update`:
   *Project settings → <project\> → Actions → Import scripts*, and import all three (*The
   scripts* below). *Worktree setup* and *Finish merged task* are the ones the task flow
   needs, *Haywire studio* is a convenience.
3. **Check**: the project's scripts menu lists *Worktree setup*, *Finish merged task* and
   *Haywire studio*, and *Import scripts* no longer shows: it shows only while some
   `t3.json` script is not imported yet.

Once a [new organisation library](../new-org-library.md) repository exists: add it as a new project, then steps 2–3.

### The scripts

| Script | When it runs | Core | A library |
|---|---|---|---|
| **Worktree setup** | T3 creates a worktree | `python3 scripts/worktree_setup.py` | core's `worktree_setup.py`, through the library's main folder |
| **Finish merged task** | a worktree thread settles | `finish` on the thread's branch | the same, core's `finish.py` |
| **Haywire studio** | you, from the scripts menu | `python3 scripts/studio.py start --browser` | core's `studio.py`, through `../haywire-repo` |

- **Worktree setup** brings the branch up to the latest default branch, runs `uv sync`
  (`--frozen` in a library), and gives the worktree's studio a port of its own. In a library
  worktree it first links core beside the worktree (`../haywire-repo`), wherever T3 put it,
  so the library's sources and its hooks find core. The session-start hook waits while the
  setup runs, up to 5 minutes, whether or not `async: false` is set. A worktree whose setup
  never started (T3 runs no script in a worktree it re-creates after a merge) gets no wait:
  the agent is told to run the setup.
- **Finish merged task** runs from the main folder: once the PR is merged it removes the
  worktree and both branches; before the merge it refuses and removes nothing.

### The agent checks the setup

With the start of each T3 thread, including the lead's and in any repository, the agent first checks T3's own settings (*Once, in T3's settings*), and lists what is wrong in its first reply (T3 does not show a hook's own message). You then change them manually in T3. `python3 dev/orchestrators/t3/doctor.py --check` in core runs the same check in a terminal. A project's scripts it does not check: T3 shows those itself (step 3).

## What this now allows

- **Tasks run in parallel, each on its own.** The lead starts a task thread per change
  (`t3_thread_launch`), each in a worktree of its own on its own branch, in core or in a
  library. A task reports to the lead's thread (`t3_thread_send`), and the lead links the
  task's PR to the thread, where T3 shows its status.
- **A worktree is ready before its agent works.** *Worktree setup* has brought the branch up
  to date, built the environment and given the worktree a studio port; in a library it has
  linked core beside the worktree. Nothing to install, in core or in a library.
- **Every thread gets the workflow by itself.** The session-start hook names your role and
  the thread's place; the hooks block destructive git commands, hold back the first
  branch, commit, push or PR until the workflow is read, and guard merges.
- **The agent works with a studio, started even mid-session.** Each thread starts the
  Farmhand bridge (`.mcp.json`). When a studio runs for the thread's folder, started from
  the scripts menu or by the agent with `dev/scripts/studio.py start`, its tools appear in
  the session; when it stops, they disappear. Each worktree's studio has its own port, so
  the lead's and every task's studio run side by side. The bridge also serves the docs the
  agent reads for each kind of task.
- **Merged work cleans itself up.** When a task's thread settles after its PR merged,
  *Finish merged task* removes the worktree and both branches.

### Starting the studio

*Haywire studio* runs in the thread's folder, the lead's main folder or a task's worktree.
Each worktree's studio uses the port *Worktree setup* wrote to its `.haywire/settings.json`,
so several run side by side; the main folder's is 8124.

It runs core's `dev/scripts/studio.py start --browser`, in a library through the core clone
beside it, the same command the agent runs ([the workflow: parallel
sessions](../workflow.md#parallel-sessions)). With `haywire-studio` from the
[umbrella](https://github.com/going-haywire/umbrella#readme) (`bin/haywire-studio`, linked
onto your `PATH` once, as its README says) that is the full studio with every library, the
worktree's own `packages/*` and `barn/*` in place of the umbrella's copies. Without it, the
studio runs from the checkout's own environment: core, or core and this library.

## Things to know

- **After a merge the lead sends nothing to the task's thread.** This overrides the
  "merged" message of the neutral flow in [Lead and tasks](../lead-and-tasks.md): a message
  resumes the thread, and if its worktree is already gone T3 re-creates the worktree and the
  branch from local `master`
  ([#198](https://github.com/going-haywire/haywire/issues/198)). The lead checks `master`'s
  CI itself and re-settles the thread; the settle script runs `finish`. A task's brief
  promises no "merged" message.
- **A thread can settle before its PR merges**, when its last turn ends. Its settle script
  then finds the PR unmerged and leaves everything. After each merge the lead unsettles the
  task's thread and settles it again, so the cleanup runs. A thread that has not settled
  yet settles when its turn ends, and the script runs then.
- **Storage cleanup** (off by default) has no hook: it removes only worktrees T3 created
  and keeps their branches; `finish --sweep` cleans those up.
- **The scripts T3 runs** are the imported copies in `~/.t3/userdata/settings.json`, under
  `projectSettingsOverrides.<projectId>.defaultProjectScripts`, not `t3.json` itself.
  - T3 before 0.1.11 dropped `async` on import, so *Worktree setup* ran alongside the agent
    ([pingdotgg/t3code#40325](https://github.com/pingdotgg/t3code/issues/40325)). On such an
    install add `"async": false` to *Worktree setup* there by hand; until then the
    session-start hook's wait covers it.
  - The agent's `t3_project_update` reports success but writes elsewhere, and T3 ignores it
    once the install has folded its project settings (`projectSettingsFolded: true`,
    [pingdotgg/t3code#14991](https://github.com/pingdotgg/t3code/issues/14991)). That is
    why the scripts are imported in the app.
- The task view (`tasks.py`) shows no session column for T3 tasks; the thread list does.
- A second machine joins as a *linked environment*; its lead is a peer.
- A worktree costs about 840 MB, most of it the `.venv`.
