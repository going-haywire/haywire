    Collaboration¶

    How work moves in haywire, from a first project on one computer to a library of the going-haywire organisation that several agents work on at once. Each process has a page with a sequence diagram (one lane per actor, your decisions numbered ①②③) and a step table whose every row links to the place that holds that step's rule or command. The pages draw; they restate no rule.

    New to branches, pull requests and CI? Start with Basics.

    The journey¶

    Each stage is useful on its own; nobody has to go further than they want.

    flowchart TD
    A["1 · haywire init"] --> S1(["stop: a private project"])
    A --> B["2 · share from your own repository"]
    B --> S2(["stop: installable from your repository"])
    B --> C["3 · publish to PyPI"]
    C --> S3(["stop: in the public shop"])
    C --> D["4 · protect your own master (optional)"]
    D --> S4(["stop: a professional own project"])
    C --> E["5 · an organisation library"]
    D --> E
    E --> F["6 · a developer's workstation"]
    F --> G["7 · pull request cycles"]
    G --> S5(["stop: one change at a time"])
    G --> H["8 · several tasks at once"]
    Stage What happens Pages
    1 · Start a project haywire init creates a project with one library, agent instructions and a dormant publishing workflow Create and first share
    2 · Share from your repository A public haybale- name, a repository on any host, then Share; others install from your repository's tag Create and first share, Share an update, Rename, then share
    3 · Publish to PyPI One-time owner steps on PyPI, then every share uploads through the generated workflow Create and first share
    4 · Protect your own master Optional guidance: releases go through a release pull request Share an update
    5 · An organisation library The repository joins going-haywire: shared CI, rulesets, the agents' dev plugin, development against core's master A new org library
    6 · A workstation Core and the libraries you work on side by side; the umbrella for several at once A developer's workstation
    7 · Pull request cycles Every change through a pull request, CI, your "merge"; releases on your "publish" A task with its live check, A change across core and a library, A core release, A library release
    8 · Several tasks at once A lead session and one session per task, each in its own worktree Lead and tasks

    Users install libraries without any of this: Subscribe and install. Outside contributors propose changes from a fork: A first contribution, and the maintainer's side of it, A fork's pull request.

    Two words decide¶

    Every change reaches master on the maintainer's "merge", and every release on their "publish": an agent never merges a release pull request on "merge". Why releases are a decision of their own: ADR 0087 and ADR 0088.
